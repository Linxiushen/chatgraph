# ChatGraph 产品与二次开发设计

状态：0.4.2-beta.1 个人工作区测试版。真实 DeepSeek V4 Pro 已接通并用受控对话验证；市场需求、留存和付费仍待真实用户验证。

## 1. 要完成的工作

用户继续在惯用的 AI 平台探索问题。讨论结束后，ChatGraph 帮他明确：最后怎么判断，为什么，哪些建议被放弃，哪些问题没解决，下一次从哪里继续。

首批聚焦用 AI 讨论产品的独立开发者、产品经理。一次完整的产品决策是最小成果，逐步形成可持续维护的个人知识。

价值验证基线：用户在原聊天窗口使用一条认真设计的总结指令。导图更漂亮并不足以证明价值；应比较达到可用成果所需的整理与核查总时间，以及后续实际复用。

## 2. 核心差异化的验收标准

| 情形 | 必须保留的行为 |
| --- | --- |
| 用户问“是不是应该做 B” | 记录为问题或待确认，不能因为用户说过 B 就认定接受 |
| AI 提出 B，用户没有回应 | B 属于 AI 建议，不能标为用户已确认结论 |
| 用户最初选 A，后来选 A2 | 保留旧判断与新判断，并建立从 A2 到 A 的修正关系 |
| 用户明确否定某建议 | 保留被否定的对象与否定的用户原文 |
| 一条陈述看起来像事实 | 只记录其来源；没有外部查证就不宣称事实已验证 |
| 生成结果缺少消息或引用 | 失败或明确提示范围不完整，不能悄悄补写原文 |
| 人工新增节点 | 标明没有原文引用，允许用户自行补充 |

语义正确性仍需人工核查。程序的引用、角色和状态检查可以排除结构错误及部分明显错归属，不能证明模型已经理解每次反讽、否定和隐含接受。

## 3. 一次完整使用流程

1. 导入对话：粘贴、文本/Markdown/JSON，或从账号导出的 conversations.json 中本地选择一个会话，核对消息范围与角色，填写可选标题、平台和来源链接。
2. 选择原文整理或 AI 结构化；前者无外部请求，后者明确使用配置的模型。
3. 在图谱、大纲、原文和观点变化四个视角中检查结构及前后变化。
4. 选中节点，修改标题、解释、归属、状态，检查引用；增加、修改或移除关系。
5. 自动保存至知识库，可恢复历史；导出 Markdown、JSON、SVG、独立 HTML 或 PPTX。
6. 下次追加新对话，保留原文批次和人工编辑，审阅 AI 建议的跨对话关系。

## 4. 界面与信息结构

界面以阅读和思考为中心：左侧知识库，中间图谱/大纲/原文/观点变化，右侧节点检查与编辑。暖白背景与安静网格，森林绿用于主要行动；节点通过文字和颜色共同区分归属与状态，避免仅靠颜色传达意义。

根主题 → 可编辑的层级节点；跨节点语义关系独立保存。节点有 label、summary、type、stance、status、sourceIds、parentId、note，可有人工布局坐标。原文消息单独存储，节点只引用真实 message ID，修改摘要不修改原文。

关系方向：包含从父到子，支持从依据到主张，反驳从反对意见到被反对对象，修正从新判断到旧判断，依赖从待完成事项到其前置条件。

## 5. Archify 的复用与扩展边界

Archify 是 typed JSON 到 HTML/SVG 的生成与验证系统，包含强大的独立阅读器；本身不负责读取 AI App 聊天，也不提供产品级思维导图编辑器。

0.2 沿用直接复用 `applyTemplate`、`esc`、`textUnits`、中文本地化和 `archify/assets/template.html`。ChatGraph 新建对话 schema、树布局、带语义属性的 SVG 导出器以及可编辑网页。

不将个人判断伪装为 architecture 的 frontend/backend/database 类型，也不将聊天原文伪装为 Git 仓库证据。所有新实现置于 `chatgraph/`；上游引擎不改动，升级前比较模板契约并运行回归。

独立 HTML 的每个节点保留 Archify 语义 ID，使阅读器可以搜索、聚焦和浏览关系。图谱之后列出观点引用及完整来源消息。

## 6. 三个入口共用一个核心

| 状态 | 入口与交付 | 当前证据与边界 |
| --- | --- | --- |
| 已实现 | 本地网页、DeepSeek V4 Pro、编辑、保存、恢复、追加、五种导出 | 单元与浏览器检查、真实模型样本；语义正确性仍须核对 |
| 已实现并在模拟宿主验证 | ChatGPT MCP + 交互组件，选配 OAuth 资源服务器 | SDK 协议与浏览器验证；尚无真实账号连接/上架结果 |
| 已实现并在 DOM 样本验证 | ChatGPT / DeepSeek 浏览器扩展、分享页面采集 | 用户点击后读取已渲染内容；不保证登录站点将来的页面结构或完整账号历史 |
| 已编译 / 尚需真机验收 | Android 原生、iOS 主 App 与分享扩展、PWA 收件箱 | 用户主动分享；需要 HTTPS 工作区，iOS 还需 Apple 签名 |
| 已提供部署代码 | 单人工作区登录、只读分享、Docker + HTTPS 配置 | 本机部署验证与外网托管是不同阶段，正式域名需实际配置 |

入口共用对话 JSON 与图谱模型。扩展明确显示采集范围，MCP 只使用模型实际传入的原文，不宣称可以读取用户账号全部历史。

这一版仍不包含：团队组织与实时共同编辑、图片/语音附件理解、服务端自动抓取分享链接、完成审核的商店分发和商业化验证。

## 7. 验证计划与开发优先级

先招募 10 位目标用户，各提供两段最近用于真实任务的聊天。对照原生总结和 ChatGraph，隐藏结果来源，让用户继续完成自己的真实工作。

记录修订与核查时间、错误归属、关键反转遗漏、一周内引用或再次使用的行为，并以真实下一次付费测试补充口头意愿。可将 6/10 选择 ChatGraph、整理核查时间减少约 30%、5/10 一周内复用作为内部迭代门槛；这是实验建议，不是行业基准。

开发优先顺序：原文可靠性 → 提取质量 → 编辑纠错时间 → 再次使用 → 分发与平台适配 → 多形式输出。0.2 已补齐基础追加、关联建议与 PPTX。0.3 增加账号导出选择、原文范围预览与角色修正，改进有界分层合并、完整关联依据与任务恢复。之后根据使用反馈优化大图布局、去重质量和多人共同编辑。真实用户研究材料见 [research/README.md](research/README.md)。

## 8. 开源与商业路径

开源可部署核心和输入输出格式，让用户可迁移数据，方便社区补充平台适配。收费假设可以围绕托管、模型额度、同步和团队协作验证。开源协议不替代第三方 API 使用条款，上架也不保证平台推荐或流量。

产品以 ChatGraph 品牌发布，公开仓库为 https://github.com/Linxiushen/chatgraph ，提供虚构示例和完整使用说明。新增代码采用 MIT 并保留上游署名；原始对话、密钥和本地知识库不进入发布内容。

产品功能取舍、工程验收证据与商用边界集中维护于 [工程验收矩阵](docs/engineering-readiness.md)。
